# Rapport Auditor: research and product direction

Research checked on 2026-10-06. Product feature pages are first-party descriptions, not independent evaluations. The security and accessibility recommendations below favor primary documentation from Flask/Werkzeug, OWASP, W3C, MDN, Python Packaging Authority, and the named design systems.

## Decisions

Rapport Auditor is an anonymous editing checklist with a loopback-only local profile and a prepared single-host public profile. Its useful niche is the combination of repetition cues, conservative copy-edit previews, visible citation cues, and LaTeX-aware input without sending the manuscript to a third-party writing service. Keep the analysis deterministic and explain each signal in plain language. A red/yellow/green verdict, numeric confidence score, or “AI likelihood” label would overstate what the current rules establish.

The implementation is a Python monorepo with `apps/api`, `apps/web`, and `packages/core`, one Flask application factory, and a bounded worker pool for analysis. Local mode binds to loopback. The prepared public profile places the app behind Caddy HTTPS and uses Redis only for shared, expiring rate-limit metadata; it adds no accounts, external writing APIs, source lookup, analytics, or remote fonts. The topology is described in [`deployment/compose.yaml`](../deployment/compose.yaml), but it is not a live or host-verified deployment. Keep `rapport_auditor` importable from `packages/core`. The project uses separate pinned runtime and development requirement locks plus the `pyproject.toml` build-system pin; do not describe it as a single-lock install. Flask’s own tutorial recommends an application factory as a project grows, and Python’s packaging guide makes `pyproject.toml` the standard location for metadata and tool configuration; `uv` workspaces are useful when there are multiple packages that really need coordinated independent boundaries ([Flask factory](https://flask.palletsprojects.com/en/stable/tutorial/factory/), [Python `pyproject.toml`](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/), [uv workspaces](https://docs.astral.sh/uv/concepts/projects/workspaces/)).

Use native HTML forms and controls with Jinja templates, scoped CSS, and a small amount of vanilla JavaScript. Preserve ordinary POST-and-render behavior without JavaScript. Add JavaScript only for convenience such as a nonintrusive word count or copy-to-clipboard; the review, upload, and revision preview must continue to work when scripts are disabled. This matches progressive enhancement guidance for form submissions ([MDN](https://developer.mozilla.org/en-US/docs/Web/Progressive_Enhancement)).

## Existing product baseline

At inspection time the project was a small Flask/Jinja application with pure Python modules for auditing, repetition, and revision. It accepted pasted text and `.tex`/`.txt` uploads, and returned server-rendered results. Nine pytest tests covered basic audit metrics, LaTeX stripping, repetition, revision preview, and a few routes. The root `requirements.txt` used open-ended `Flask>=3.0` and `pytest>=8.0` constraints without a lock file.

Historical baseline at the initial research review (before the bilingual rule-set and public-profile work): the phrase lists, transitions, jargon terms, claim markers, and sentence patterns were predominantly English. The old implementation also exposed “style risk” and an uncalibrated `confidence_level()` based on fixed word/sentence thresholds. Those values did not measure finding correctness. The current interface/API use limited English or French rule cues and do not expose risk or confidence scores. Synthetic examples test rule behavior only; they do not establish real-world reliability. Neither the current nor historical rules learn a user's voice or identify authorship.

Likewise, the current citation routines recognize visible LaTeX `\cite` commands and look for claim words, dates, and numbers. They neither resolve citation keys nor inspect bibliography records nor verify that a cited source supports a nearby claim. The public result should call these **source-check prompts** or **citation cues**. It should explicitly say that a cue has not opened, matched, or assessed the source. A visible citation can be missing in another style, and a present citation can still be irrelevant.

Historical input-boundary finding: the initial handler read an uploaded stream fully before slicing it to 250,000 characters, and pasted text was silently sliced. The current app instead enforces request-byte and decoded-character limits and rejects overflow. Flask documents `MAX_CONTENT_LENGTH`, `MAX_FORM_MEMORY_SIZE`, and `MAX_FORM_PARTS` as distinct resource controls; the first caps the whole request, while the form-memory setting concerns non-file multipart fields ([Flask security](https://flask.palletsprojects.com/en/stable/web-security/), [Flask upload handling](https://flask.palletsprojects.com/en/stable/patterns/fileuploads/)).

Historical upload-buffering finding: default Werkzeug upload streams may spill to temporary storage. The current request class gives accepted uploads bounded in-memory streams, and the Waitress limits are configured to keep accepted request and response buffers below its spill thresholds. This describes the application/server configuration, not host-level guarantees: operating-system paging, crash dumps, container/runtime behavior, and infrastructure telemetry remain outside the app's control. Keep the conservative no-intentional-retention wording in the README. The original behavior and general framework caveat are documented by Flask and Werkzeug ([Flask uploads](https://flask.palletsprojects.com/en/stable/patterns/fileuploads/), [Werkzeug request objects](https://werkzeug.palletsprojects.com/en/stable/wrappers/)).

These product descriptions are useful workflow references, not proof that their accuracy or privacy claims transfer to Rapport Auditor. Their recurring, transferable pattern is actionable feedback attached to the text: category → exact passage → concise reason → writer-controlled next step. Keep that pattern and be much narrower in claims.

### Citation and academic-integrity boundary

Crossref offers free metadata retrieval and reference matching that can help match deposited reference metadata to DOI records. Its own documentation explains that reference matching is based on metadata, and that matched records differ depending on coverage and matching methods ([Crossref metadata retrieval](https://www.crossref.org/documentation/retrieve-metadata/), [reference linking](https://www.crossref.org/services/reference-linking/), [matched references](https://www.crossref.org/documentation/retrieve-metadata/retrieving-identifiers-for-deposited-references/)). This is not the same as verifying a paper’s argument or whether a source supports a particular sentence. Crossref’s Similarity Check is a separate member service powered by iThenticate, not a property of local text heuristics ([Crossref services](https://www.crossref.org/services/)).

Avoid any AI-authorship detector framing. OpenAI retired its own experimental classifier because of low accuracy; its published evaluation reported 26% true positives and a 9% false-positive rate on its English challenge set ([OpenAI classifier notice](https://openai.com/index/new-ai-classifier-for-indicating-ai-written-text/)). A peer-reviewed study in *Patterns* found high false-positive rates on non-native English essays for several evaluated detectors ([Liang et al., 2023](https://doi.org/10.1016/j.patter.2023.100779)). Rapport Auditor’s rule lists are much narrower than those classifiers, but the same product-risk lesson applies: pattern cues cannot establish authorship, and a categorical label can unfairly stigmatize legitimate writing. Preserve “editing checklist” language and avoid academic-integrity adjudication.

Suggested user-facing scope statement:

> In local mode, Rapport Auditor runs on your computer. In the public profile, text is sent to the hosting server over HTTPS for processing. The application is designed not to retain drafts; uploaded files and results may be temporarily buffered while a request is processed. It points out selected English or French writing patterns and claims you may want to review. It does not detect plagiarism or authorship, verify facts, look up sources, or check that a source supports a claim. Review every suggestion and keep your original file until you decide what to use.

If the statement about temporary buffering is included, use the fuller privacy wording from the section above. Avoid “fully private,” “zero data stored anywhere,” “accuracy,” “confidence,” and “submission ready.”

## Product ideas, ordered by value and cost

1. **Trust and orientation.** Explain what each check can and cannot tell the user before they submit. Show the source type, selected report language, detected word/sentence counts, and the narrow scope of the English/French rules. Display textual evidence and an explicit next question (“Does this claim need a citation?”), not a verdict.
2. **Better review navigation.** Group results by “repeated wording,” “style patterns,” and “source checks.” Add keyboard-friendly in-page links to each group, result counts, and a clear empty state that says what was checked. Avoid a row of fake-precision risk gauges.
3. **Reversible revision review.** Present each proposed edit as “Before / Suggested wording / Why this changed.” Keep accept/reject or copy actions explicit; never mutate an uploaded or pasted source automatically. An overall unified diff can remain available as a secondary detail.
4. **Helpful LaTeX context.** Retain citation keys and line numbers for `.tex` findings where the existing parser can identify them. Explain that parsing is best-effort and that custom commands, bibliography formats, comments, macros, and material outside the selected English/French rule set may be missed. Never compile uploaded LaTeX or execute commands.
5. **Bilingual rules with honest boundaries.** Keep UI locale separate from selected report language. The engine has small English and French cue sets, not broad comprehension, grammar correction, or translation. Synthetic fixtures cover their expected examples but do not demonstrate equivalent real-world performance; communicate that limitation without presenting numeric accuracy or confidence scores.
6. **Optional future citation lookup, only if requested later.** A narrowly scoped, user-initiated DOI metadata lookup might help resolve bibliographic records. It would require clear consent because citation strings would leave the machine and metadata coverage is incomplete. It still could not validate source-to-claim alignment. It is excluded from this modernization.

## UI, components, and template references

Use component guidance as a reference and implement a small purpose-built layer. A full prebuilt product shell would add dependencies and visual conventions without solving the app’s core problem.

- [GOV.UK form and error guidance](https://design-system.service.gov.uk/components/error-message/) recommends matching an error to its field, explaining the fix, and preserving entered values; its [error summary](https://design-system.service.gov.uk/components/error-summary/) moves keyboard focus to the error list and links each error to its control. These patterns fit the paste/upload form well.
- The [GOV.UK textarea](https://design-system.service.gov.uk/components/textarea/) and [character-count component](https://design-system.service.gov.uk/components/character-count/) are good references for persistent labels and count messaging. The guidance says to use a live count only when there is a real technical/business limit and to allow paste, then report overflow clearly. If the count is implemented, enforce the same limit on the server.
- [USWDS forms](https://designsystem.digital.gov/components/form/) advise vertical form structure and contextual helper/error text. Its [design tokens](https://designsystem.digital.gov/design-tokens/) offer a useful method: define a restrained palette and spacing/type scales by semantic purpose, rather than introducing many one-off values. USWDS is a government design system; use its form/accessibility research, not its visual identity wholesale.
- Native `<form>`, `<label>`, `<textarea>`, `<input type="file">`, `<button>`, `<ol>`, `<dl>`, and `<details>/<summary>` cover this app’s existing functions. Keep results as headings, lists, or definition lists rather than turning every item into a chart. Use text labels in addition to color, persistent field labels, visible keyboard focus, and controls large enough for touch. WCAG 2.2 AA minimum target size is 24×24 CSS pixels with exceptions; 44×44 is the more comfortable project target ([W3C Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)).
- [Radix Primitives](https://www.radix-ui.com/primitives/docs/overview/introduction) are React components. [shadcn/ui’s Astro setup](https://ui.shadcn.com/docs/installation/astro) configures Tailwind and React; the repository has neither and needs no complex widget, so adopting this path would create a second runtime without meaningful benefit.
- [Flowbite](https://flowbite.com/docs/getting-started/quickstart/) works with Tailwind and vanilla JavaScript, but still brings a library, utility-CSS setup, and initialization lifecycle for interactions the native controls already provide. It is not recommended for this interface.

## Suggested agent skills and research resources

Skills are optional development-time guidance, not app dependencies. The active environment catalog included OpenAI’s `security-best-practices`, `security-threat-model`, `playwright`, and `playwright-interactive` skills; no global installation is needed to use the available environment tools.

- Use [OpenAI `security-best-practices`](https://github.com/openai/skills/tree/main/skills/.curated/security-best-practices) for framework-aware review of the Python/Flask boundary and [OpenAI `security-threat-model`](https://github.com/openai/skills/tree/main/skills/.curated/security-threat-model) to record repository-specific assets, entry points, trust boundaries, and mitigations. These are security tasks rather than generic style review.
- Use [OpenAI `playwright`](https://github.com/openai/skills/tree/main/skills/.curated/playwright) for repeatable terminal-driven browser QA and [OpenAI `playwright-interactive`](https://github.com/openai/skills/tree/main/skills/.curated/playwright-interactive) for persistent visual/interaction debugging when that tool is available. The former’s current workflow is CLI-oriented; the latter depends on an enabled persistent JavaScript REPL. Keep test code and dependencies in the repository only when the project needs them.
- [Anthropic `frontend-design`](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md) gives useful framework-agnostic guidance on choosing a visual identity from the product’s subject, writing concise UI copy, and reviewing the implementation. Pair it with formal accessibility requirements; it is aesthetic direction, not a conformance standard.
- For visual review use the first-party [GOV.UK Design System](https://design-system.service.gov.uk/components/) and [USWDS](https://designsystem.digital.gov/components/) pages above. For normative requirements use the [WCAG 2.2 Recommendation](https://www.w3.org/TR/WCAG22/), not a design-system example alone.

## Source and method limits

The competitor section reports the vendors’ own descriptions and should not be read as a neutral feature audit. Security recommendations were checked against Flask 3.1 documentation, Werkzeug 3.1 documentation, OWASP guidance, and W3C accessibility material current at the research date. Do not use examples that contain real student submissions in screenshots or fixtures. Use short synthetic text whose authorship and references are known.
